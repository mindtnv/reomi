# Второй проход: результаты реализации

Источник критериев: [аудит из 120 пунктов](spaced-repetition-audit-round-2.md). Реализация: `openspec/changes/complete-spaced-repetition-polish`. Незакрытые критерии остаются открытыми; этот отчёт не означает готовность всех 120 пунктов.

## R2-001 — закрыт

`sanitizeFieldValues` сохраняет Markdown как исходный текст, включая code/HTML-примеры, сравнения, entities и Unicode. Отдельная HTML-функция и её allowlist сохранены для явных HTML-вызовов. Client parser с `html:false` и обязательный DOMPurify sink защищают отображение; имена полей копируются без потери `__proto__`.

До исправления новые source tests воспроизводили потерю `<T>`, `<button>`, `<script>` и преобразование entities. После исправления POST → GET → PATCH → GET проверен через настоящий API/PostgreSQL; DOM-проверки сохранённого source не обнаруживают исполняемых script/svg/iframe/handlers или внешних img.

Проверка: Bun **1.3.14**, committed migration chain на изолированной `neuronexus_srs_test`; **173 passed, 0 failed**, 522 assertions в 6 файлах: notes, markdown-source API/web, sanitize API, sanitize-img API/web. Strict OpenSpec: 6/6. Это проверка данного среза, не финальный полный gate.

Уже потерянные прежней очисткой символы автоматически не восстанавливаются. Исправление производного поискового текста выполняется отдельно в R2-002.

## R2-013 — закрыт

Поля получают постоянные идентификаторы в существующем JSON; старые определения получают детерминированные legacy IDs при чтении. Переименование атомарно переносит ключи значений всех заметок и ссылки/условия шаблонов. Редактор сохраняет идентичность при перестановке и обновляет preview. Совпадение с уже сохранённым скрытым полем отклоняется до любых записей; ambiguous rename старого клиента без ID требует актуальное определение.

API-регрессия проверяет rename после grade, неизменные ID/due/reps/stability, отклонение повторяющихся имён и полную сохранность при коллизии. Четыре unit-проверки покрывают legacy IDs, секции, одновременную перестановку имён и коллизии.

## R2-015 — закрыт

Шаблоны имеют стабильные ID в JSON. Перестановка/переименование пересопоставляет ord по ID, сохраняя карточки и FSRS. Меняющиеся ord сначала освобождаются внутри транзакции, поэтому будущий unique constraint не помешает обмену позициями. Удаление используемого шаблона пока отклоняется с `template_removal_requires_preview`; полноценное подтверждаемое удаление и регенерация остаются открытым R2-014.

Красный тест показывал, как Forward получал вопрос Reverse с прежней историей. Зелёный проверяет обе стороны после одновременного rename и reorder. Обновления времени карточки монотонны. Новый schema column для JSON-идентификаторов не потребовался.

## R2-097 — закрыт

Миграция `0026_nebulous_havok.sql` делает исторический `reviews.deck_id` nullable с `ON DELETE SET NULL`. Владение review определяется пользователем и карточкой; удаление самой карточки по-прежнему удаляет её reviews. API/export допускают отсутствующую историческую колоду, клиентский Review и агрегирование обновлены.

Тест grade в A → move в B → delete A сначала терял review, после миграции сохраняет ID/rating/cardId с deckId=null и прежнее расписание карточки. Чужой пользователь не видит эту историю. После изменений: **37 API-тестов прошли**, 161 assertion (notes, note-types, review-safety); typecheck всех workspace прошёл. Миграция применена только к изолированной test-базе.

Откат R2-097: nullable FK можно оставить при откате совместимого приложения. Возвращать NOT NULL/CASCADE поверх появившихся null-строк нельзя без отдельного плана восстановления; не удалять исторические reviews ради отката. Ранее каскадно удалённые повторения не восстанавливаются этой миграцией.

## R2-002 — закрыт

Поисковые поля формируются из разобранного Markdown каждого поля, затем удаляется структура шаблона и однократно декодируется текст. Inline/fenced code сохраняет `<T>`, обратные слеши, pipes и буквальные entities. Изображение индексируется по alt, без storage URL; пустой alt не уничтожает действительный image-only вопрос. Обычный HTML в Markdown остаётся буквальным текстом, как и на экране.

Добавлен `apps/api/src/ai/rebuild-card-text.ts`: обязательная область userId, страницы по 200, условная запись по версии карточки, повторяемость. Опциональный `--reindex` дожидается существующего embedding worker batch, проверяет также неизменные строки при повторной попытке и использует штатную проверку capability/hash. API-тест проверяет чужую область, испорченный старый cache, повторный запуск, неизменные source/due/reps/updatedAt. Без флага платных запросов нет.

## R2-003 — закрыт

Общий `cardMathPlugin` разбирает математическую разметку внутри Markdown grammar. Inline, fenced и indented code остаются буквальными; literal HTML attributes и URL не становятся формулами. Обычные формулы, в том числе display math с пустыми строками, проходят тот же безопасный KaTeX sink.

Новые красные проверки воспроизводили `.katex` внутри code и потерю delimiters. После исправления пройдены функциональные и security corpora: 190 тестов shared/render/sanitizer, затем дополнительные display-block проверки. Typecheck всех workspace прошёл.

## R2-014 — безопасная регенерация типа

Один общий planner сопоставляет существующие карточки с будущими по стабильной идентичности. Preview показывает create/keep/delete, число удаляемых reviews и до 50 конкретных удаляемых вопросов. Применение создаёт недостающие карточки, сохраняет ID/FSRS оставшихся и удаляет только подтверждённые. Удаление или превращение вопроса в пустой больше не оставляет карточку без действующего шаблона. Заметке без карточек для выбора колоды требуется отдельное восстановление (R2-080); операция не пропускает её молча.

`POST /note-types/:id/preview` не записывает данные. PATCH проверяет hash текущего плана и его исходных строк; grade между preview/apply делает прежнее согласие недействительным. React-тест проверяет конкретный вопрос/число повторений, защиту от двойного клика и передачу того же token. Добавление/удаление шаблона проверены через реальный API/БД с сохранением расписания оставшейся карточки.

## R2-020 — согласованность открытых карточек

После изменения типа одним обновлением store публикуются новое определение и свежие карточки: первая страница данного типа плюс bounded lookup уже загруженных глубоких карточек. Удалённые карточки исключаются. Последующая операция над типом и reset аккаунта отменяют право старого ответа обновить зеркало. Read generation не позволяет старому search/refetch воскресить удалённые строки. Browser повторяет авторитетный поиск после смены каталога типов.

Раскрытый reviewer сохраняет показанный вопрос/ответ, блокирует оценку и предлагает обновить очередь при изменении его типа. Проверены deep-card refresh, новые/удалённые карточки, delete во время старого refresh, ошибка фонового чтения и поздний search. API lookup принимает максимум 200 UUID, дедуплицирует их и не возвращает чужие карточки; фильтр noteTypeId также user-scoped.

## R2-021 — обновление индекса после изменения типа

После успешного commit enqueued только новые карточки и реально изменившийся renderText. No-op/style-only изменения не запускают enqueue; удаление карточки каскадно удаляет kb_chunk. Интеграционная проверка со spy на существующей очереди и настоящим kb_chunk подтверждает отсутствие enqueue у preview/style-only, точные изменившиеся ID и удаление старого индексного ряда.

## R2-024 и R2-026 — конфликты редакторов

Типы и заметки имеют передаваемую версию updatedAt. Старый редактор получает 409 вместо перезаписи новых данных. Его draft остаётся на экране; отдельно показаны актуальные поля/шаблоны для сравнения и копирования. Замена draft либо осознанное принятие новой основы требует явного действия. Следующее сохранение снова проходит preview. Собственный успешный save обновляет базовую версию формы.

API-тесты проверяют two-editor overwrite и неизменность текущих данных; React-тесты — сохранение локального текста, показ другой версии и отправку новой expectedUpdatedAt только после решения пользователя.

## R2-028 — удаление дочерних карточек при правке заметки

`POST /notes/:id/preview` считает реальную историю, в том числе сохранённые reviews после ручного Forget. Изменение полей, убирающее вопрос, требует того же consistency token в PATCH. Простой текстовый edit без удаления не вызывает диалог. Отмена preview оставляет draft и не отправляет write. Проверены read-only preview, отказ без token, stale token после grade и успешное подтверждённое удаление.

AI-путь также сохраняет server-generated token в pending tool-call JSON, не принимает его из model args и сверяет при resume. Изменение заметки после предложения приводит к отказу без мутации. Поля и перенос карточки применяются в общей транзакции; устранено ожидание собственного lock при обращении к глобальному db вместо tx. Пройдены 11 agent-confirm тестов, включая stale confirmation и совместное edit+move.

## R2-100 — согласование типа и записи заметки

Внутренние create/update проверяют версию определения после получения lock; порядок — type → note → cards. Все вызовы, включая AI и reading/harvest, передают версию, по которой генерировали карточки. Устаревшее разрешение create/update отклоняется до записей. При удалении типа последующая запись не возвращает исчезнувшую заметку. Контролируемые interleavings тестируют resolve → type change/reorder/delete → commit; результатом является согласованное состояние либо conflict, без частичной записи.

Дополнительно уточнён R2-002: PostgreSQL хранит микросекунды, JS Date — миллисекунды. Условный backfill теперь сравнивает поддерживаемую миллисекундную версию и чинит также never-reviewed строки; специальный тест использует timestamp `.123456` и проверяет сохранение reps=0.

## R2-004 — независимые cloze-вопросы

Новая заметка создаёт отдельную карточку для каждого номера на лицевой стороне шаблона. Повторяющийся номер объединяет пропуски; у каждого вопроса собственные ID и FSRS. Добавление номера не пересоздаёт прежние карточки, удаление номера проходит обычный preview с подсчётом затронутой истории.

Миграция `0027_dazzling_madame_masque.sql` маркирует прежние общие вопросы числом 0 без изменения остальных полей. Они остаются общими до явного разделения. В preview пользователь выбирает наследника истории отдельно для каждого старого шаблона (`clozeRetainHistoryFor`); выбранный вопрос сохраняет ID/историю/расписание, остальные начинают с нуля. Неполное отображение или смена решения без нового token отклоняется. Старые записи без номера от прежнего API также распознаются как общие. Старое c0 остаётся читаемым, хотя новые независимые вопросы требуют положительных номеров.

API-регрессии проверяют независимую оценку c1/c2, сохранение ID при добавлении c3, удаление ровно нужной истории, разделение 0/null legacy, разные номера в нескольких шаблонах и stale type version. В UI выбор истории явно подтверждается кнопкой разделения, а не ложной кнопкой удаления.

## R2-005 и R2-006 — грамматика и буквальные примеры

Вместо плоской регулярки работает ограниченный сбалансированный разбор: подсказка отделена от ответа, фигурные скобки и вложенные пропуски не обрываются. Допускается до 8 уровней и 128 сгенерированных вопросов на заметку; превышение отклоняется явно. Формулы с cloze преобразуются до KaTeX и не раскрывают ответ на вопросной стороне. Общая глубина учитывается и на границе Markdown/math.

Inline/fenced/indented code остаётся буквальным. Номера поступают из разобранных полей, реально используемых лицевой стороной, а не из HTML-атрибутов шаблона: добавленный регрессионный пример с `data-nn-cloze="99"` больше не создаёт ложный вопрос. Некорректный новый текст не записывается; некорректный старый показ выдаёт понятную ошибку без падения и частичного раскрытия ответа. Скрытые и неиспользуемые Mermaid-блоки не рендерятся заранее.

## R2-029 — полный предпросмотр

Редактор показывает число фактически создаваемых вопросов и позволяет выбирать любую пару шаблон/номер, включая обратную карточку. При переключении ответ снова скрыт. Пропущенные необязательные шаблоны перечислены с объяснением. React-тесты проверяют c1 → раскрытие → c2, обычный reverse и выбранное направление переноса legacy-истории.

## R2-099 — уникальность вопроса

Введён versioned `UNIQUE NULLS NOT DISTINCT (note_id, template_ord, cloze_number)`: в текущей версии типа каждой позиции соответствует один стабильный ID шаблона; смена позиций выполняется атомарным сопоставлением этих ID. Один вопрос не может появиться дважды, обычное null-значение также защищено. Перестановки шаблонов и разделение cloze проходят под этим ограничением.

Проверена полная миграция на отдельно созданной временной БД: цепочка до 0025 → старый aggregate с расписанием и review → намеренный дубль → отказ 23505 с сохранением обеих строк и истории → удаление только синтетического дубля → успешная и повторная миграция. JSON-снимки всех старых полей карточки и истории полностью совпали по значениям. Временная БД удалена самим проверочным сценарием. SQL-регрессии в `cloze-migration.test.ts` повторяют сохранность/отказ на изолированных transaction-local таблицах; API-тест проверяет сам constraint.

## R2-008 — честное оформление

Убрана возможность редактировать CSS, который всё равно не применялся. Интерфейс объясняет, что карточки используют тему приложения. Ранее сохранённый CSS доступен только для чтения, сохраняется при правках типа и остаётся в экспорте. Проверка подтверждает отсутствие редактируемого CSS-контрола и сохранение исходного значения в PATCH; произвольный CSS в рендер не добавлялся.

## R2-012 — темы диаграмм

Mermaid использует default/light либо dark по фактическому `data-theme-mode` и наблюдает смену семейства. Старый асинхронный результат не может заменить новую диаграмму. Пока идёт построение, показывается локализованная загрузка, а не внутренний placeholder ID. SVG проходит прежний sanitizer.

Проверены live theme switch и delayed-result race в React, плюс 99 renderer/security тестов. Реальная конфигурация установленного Mermaid даёт контраст базового текста/узла **16.07:1** для default и **12.28:1** для dark. Реальный тёмный SVG «Повтор → Память» проверен визуально в браузере. Это не заменяет отдельные будущие проверки VoiceOver/физического iOS.

Токен SHA-256 связывает операцию, владельца, определение, состав/содержимое заметок и карточек, историю повторений. Замена заметки при прежнем общем количестве тоже делает подтверждение устаревшим.

В одной транзакции блокируются существующий профиль → тип → заметки → карточки → повторения, проверяется актуальный снимок и выполняется каскад. Новая оценка, изменение исходника или преобразование заметки после preview дают 409 без удаления. Глобальные и чужие типы — 404. Те же ограничения ожидания/SQL/работы, что у редактирования, обеспечивают полный rollback при таймауте. Тест намеренно задерживает AFTER DELETE trigger карточки и подтверждает сохранность типа, заметок и карточек после отмены каскада.

Диалог получает серверные числа до включения действия удаления. Предлагает преобразовать заметки через список с точным `noteTypeId` или скачать существующий JSON-экспорт аккаунта; заметки без карточек явно отнесены к экспорту. Ошибка preview блокирует удаление. Устаревшее подтверждение сбрасывается и требует отдельного обновления последствий и нового решения. При потере ответа предлагается обновить фактическое состояние; старый token не переиспользуется. Поздний ответ после закрытия не возвращает диалог. Экспорт не запускает DELETE; перенос использует уже проверенный field/card mapping.

API-проверки: 701 заметка, 700 карточек, 700 повторений и чужая коллекция; read-only preview; отказ без токена; чужие/глобальные/несуществующие типы; новая оценка и смена исходника; одинаковые counts при новом составе; преобразование одной заметки перед удалением прежнего типа с сохранением ID/FSRS/истории; rollback каскада. ## R2-025 — восстановление незавершённых черновиков

Редакторы заметок и типов сохраняют локальные записи v1: владелец, note/type ID (отдельный `new` для создания), revision UUIDv7, время и полный исходник с исходной версией. Поля Markdown, теги, выбранный тип/колода, альтернативы Type-in и выбор наследника legacy-cloze не обрезаются. Для заметки сохраняется определение типа, по которому автор редактировал текст; его обновление после reload не подменяет исходную версию. Для типа сохраняются поля, шаблоны, styling и kind. Это локальный recovery, не офлайн-запись на сервер.

Пределы: 256 KiB сериализованного UTF-8 на запись, 10 записей / 1 MiB на аккаунт. Прежняя работа не вытесняется при переполнении. Autosave через 300 мс дополняется flush на pagehide, beforeunload и unmount. Ошибка storage/лимита видна; неподтверждённый текст остаётся в форме, может быть скачан прямо из памяти, а недоступное сохранение защищает выход native beforeunload. Управление заполненным хранилищем можно открыть в новой вкладке, не покидая текущий несохранённый текст.

После загрузки предлагаются «Восстановить» / «Отбросить»; до выбора нельзя записать поверх найденного черновика. Восстановление не запускает API-запись. Старые source/type versions участвуют в обычном конфликтном workflow; новые определения не скрывают сохранённые дополнительные поля. Исходник этих полей остаётся видимым, его можно перенести в нужное поле или явно убрать. Для существующей заметки восстановление неизменённого выбора колоды использует текущую колоду открытой карточки, вместо неявного переноса её направлений назад.

App navigation, ссылки, выход из аккаунта, prev/next, закрытие dock и переход к похожей карточке проверяют незавершённые изменения: сохранить на сервере / оставить локально / отбросить / остаться. Неуспешная запись удерживает редактор. Native history/reload сохраняет текст через lifecycle flush; исходная карточка также доступна через ссылку в списке черновиков. Bootstrap завершается до появления редактируемой формы; смена владельца/карточки переоткрывает её состояние. Поздний подтверждённый save очищает только исходный совпадающий revision, не новый черновик и не другой аккаунт. Отдельно закрыта утечка late `addNoteType` в зеркало следующего аккаунта (часть R2-101; сам большой пункт остаётся открытым).

`/editor?drafts=1` показывает только записи текущего владельца, включая текст исчезнувших заметок/типов. Доступны просмотр исходников, JSON-скачивание и явное удаление конкретного draft с проверкой revision. Повреждённые/чужие envelopes не раскрывают содержимое. Удаление оригинала не отнимает доступ к локальному тексту; при этом восстановление серверной истории не обещается. В карточках и списке типов есть прямой переход к черновикам.

Тесты покрывают lifecycle-flush/reload, создание отдельно от редактирования, точный source и версии, смену аккаунта, поздний save, другой card direction той же заметки, failure→success cleanup, отмену/keep/discard/save при уходе, возврат к исходному тексту, отказ хранилища, stale revision, квоты без удаления прежних записей, type-draft, orphan-source download и локализованные состояния. Используется реальный React + storage API тестовой DOM-среды; API-тайпчекинг и регрессии SRS сохранены.


Native QA: в редакторе и панели карточки проверены keep → повторное открытие → restore → reload → подтверждённый save → очистка draft. Восстановленный исходник совпал полностью; временные QA-изменения возвращены к исходному тексту. Отдельная регрессия сохраняет восстановленный текст, даже если он совпал с устаревшим cached baseline перед обновлением карточки. R2-025 закрыт: **33/120**, остаётся **87**.

## R2-101 — поздний ответ прошлого аккаунта не попадает в зеркало

`reset()` при смене аккаунта увеличивает `bootstrapGeneration` и очищает зеркало. Часть записей уже сверяла это поколение до `set`. Оставшиеся методы колоды, карточки, тегов, пресетов и отфильтрованных колод делали `set` после `await` без сверки, поэтому ответ аккаунта A успевал переименовать, удалить или дополнить зеркало B. `searchCards`, `refetchCard` и `refetchDeckCards` уже смотрели на `cardReadGeneration`, который `reset()` тоже увеличивает; теперь они дополнительно требуют то же поколение аккаунта.

Запись выполняется только если поколение, снятое до запроса, совпадает с текущим. Устаревший ответ не бросает исключение и не меняет зеркало или счётчики тегов. Методы, которые и раньше возвращали серверный объект, по-прежнему его возвращают. Тот же аккаунт по-прежнему записывает колоду, теги и результат поиска.

Открытый browser карточек живёт внутри `AuthenticatedWorkspace`: смена владельца размонтирует маршрут (`key={owner}`) и монтирует его заново уже на зеркале нового аккаунта. Поздний поиск, переименование, удаление и теги прошлого аккаунта не попадают ни в это дерево, ни в зеркало. Локальная подстановка поиска дополнительно сверяет поколение на случай ответа до размонтирования. Прямые `useNN.setState` после ответа сети в колодах (иерархия, оформление, перенос, переименование), в сверке профиля повторения и в транспорте ассистента сверяют то же поколение, снятое до запроса. Повторный вход того же пользователя тоже увеличивает поколение, поэтому ответ прошлого сеанса не переписывает новое зеркало; новое действие того же сеанса по-прежнему записывается.

Изменение только в web. Схема, маршруты и тела ответов API не менялись. Старый и новый клиент работают с текущим API; отдельный порядок выкладки API перед web не нужен. Откат — только web.
