# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All commands run from the repo root via **Bun workspaces**:

- `docker compose up -d postgres` — start Postgres before anything else touches the DB
- `docker compose up -d minio createbuckets` — start disposable local S3 and create the media bucket
- `bun run dev` — runs `apps/web` (:3001) + `apps/api` (:3000) in parallel
- `bun run dev:web` / `bun run dev:api` — single workspace
- `bun run build` — `next build` + `bun build` for api
- `bun run typecheck` — `tsc --noEmit` across every workspace
- `bun run test` — **full test suite** (FSRS units + API integration). `pretest` applies the committed migration chain to the test DB (`db:migrate:apply:test`).
- `bun run test:ci` — the same suite **without** a lifecycle hook; CI runs it only after `db:migrate:apply:test`
- `bun run test:s3:ci` — real media/source S3 round trips; requires reachable MinIO/S3 and fails instead of skipping when it is absent
- `bun run test:unit` / `bun run test:api` — narrow to one package
- `bun run e2e` runs the Playwright smoke (sign up, sign in, deck, card, review, statistics) described in `.cursor/skills/verify-reomi/SKILL.md`. Run that skill before a pull request that changes UI or API behavior. `bun run e2e:prod` repeats the walk on `https://app.reomi.ru` and skips with a warning when `E2E_EMAIL` or `E2E_PASSWORD` is unset. The run keeps traces off and fails if the password appears in its artifacts.
- `bun run spec:validate` — strict, non-interactive validation of every OpenSpec change and main spec
- `bun run db:push` — destructive Drizzle schema sync against `TEST_DATABASE_URL` only; never connects to `DATABASE_URL`
- `bun run db:push:test` — same test-database schema push
- `bun run db:generate` / `db:migrate:apply` — generate and apply the committed migration chain for prod (`db:migrate` remains the direct drizzle-kit command)
- `bun run db:seed` — seed local demo/reference data
- `bun run db:studio` — drizzle-kit Studio

Ports: web **3001**, api **3000**, postgres **5432**. Swagger UI at `http://localhost:3000/docs` — use it instead of curl when poking new endpoints.

Prereqs: **Bun 1.4.2**, Docker, and a root `.env` (copy from `.env.example`). The pinned baseline is TypeScript 7.0.2, Next.js 16.3, React 19.3, Node 26 Current for the standalone web runtime, and PostgreSQL 18 + pgvector 0.8.2. Pull requests gate on OpenSpec validation + `bun run typecheck` + migration-faithful `bun run test:ci` + `bun run build` and a separate real-S3 round-trip job; pushes to `main` run the same gates while both production images build in parallel. No linter configured.

## OpenSpec

OpenSpec 1.13.1 is pinned as a root dev dependency and uses the `spec-driven` schema. Use it when work adds or changes a durable externally observable capability/requirement, changes API/data/deployment compatibility, or needs alignment on a material architecture decision before implementation. Do not create a change merely because a diff is large or cross-cutting: bug fixes, technical UX hardening (loading/flicker/race fixes), pure refactors, performance work that preserves behavior, test/docs-only work, and mechanical dependency bumps proceed directly with proportionate tests. If no spec-level behavior changes, do not invent a capability to satisfy the workflow. Do not backfill the shipped product wholesale — `openspec/specs/` grows as completed changes are archived.

- Codex entry points are the generated `$openspec-*` skills under `.agents/skills/`; Claude Code exposes matching `/opsx:*` commands and skills under `.claude/`. Start a change with `$openspec-propose` (Codex) or `/opsx:propose` (Claude).
- Planning lives in `openspec/changes/<change>/`: proposal → capability specs + design → tasks → implementation → archive. Inspect state with `bunx openspec status --change <change>` and validate continuously with `bun run spec:validate`.
- Treat capability specs as observable contracts and `tasks.md` as the implementation checklist. Keep task checkboxes current while applying a change.
- `.agents/skills/openspec-*`, `.claude/skills/openspec-*`, and `.claude/commands/opsx/` are generated by the pinned CLI; do not hand-edit them. After intentionally upgrading OpenSpec, run `bunx openspec update` and commit the regenerated files with the lockfile.

## Production

- **Reomi domains**: the canonical hosts are `https://app.reomi.ru` (web) and `https://api.reomi.ru` (API). Follow `docs/reomi-domain-migration.md`. `WEB_ORIGIN` and `BETTER_AUTH_URL` stay on those hosts. The former API host is a removable Coolify and DNS alias and is not a supported client endpoint. The web host `neuronexus.mihailantonov.pro` still redirects to the app. S3 allows both web origins; database, storage and secrets are unchanged. Users sign in again on the new origin; local preferences/drafts and installed PWAs do not transfer.
- **Browser storage prefix**: persistent localStorage and sessionStorage keys described below as `nn:…` are written as `reomi:…`. A missing `reomi:` value is copied once from the matching `nn:` key; the old key is never deleted or updated afterwards. An empty `reomi:` value is a tombstone and is not refilled. Window events (`nn:toast`, `nn:open-drawer`, `nn:open-palette`, `nn:appearance`, and the rest) and the history marker `nnNavigation` keep the `nn` prefix.
- **Versioned migrations**: edit schema → `bun run db:generate` → commit the `packages/db/src/migrations/*.sql` files. Apply via `bun run db:migrate:apply` (calls the programmatic `packages/db/src/migrate.ts`). CI runs `db:migrate:apply:test` before `bun run test:ci`; `test:ci` has no `pretest` hook, so a missing migration cannot be masked by schema push. The default local `bun run test` uses that same chain: `pretest` runs `db:migrate:apply:test` and does not push. **`drizzle-kit push --force` is not a substitute for the chain through `0042_youtube_source.sql`.** Push cannot replay ordered SQL, so it drops the `0020_known_klaw.sql` notebook/source backfill, the `0027_dazzling_madame_masque.sql` `UNIQUE NULLS NOT DISTINCT` cloze constraint, and the `0038_fancy_yellowjacket.sql` revision triggers (they are not represented in the Drizzle schema). `--force` can also drop other hand-written objects already present in the target database. Schema push connects only to `TEST_DATABASE_URL` and refuses `DATABASE_URL`.
- **UUIDv7 IDs**: all new domain UUID primary keys use PostgreSQL 18's native `uuidv7()` default (`packages/db/src/schema/app.ts`; migration `0023_complex_vance_astro.sql`). Better Auth's text primary keys and server-created IDs use `newUuidV7()` from `@reomi/shared` (the cross-runtime `uuid` package). Existing UUIDv4/base62 rows remain valid and are not rewritten. Do not use Drizzle `defaultRandom()` or `crypto.randomUUID()` for persistent IDs; ephemeral test fixtures and DOM-only collision tokens are exempt.
- **Rate limiting**: `apps/api/src/rate-limit.ts` — IP-based, in-memory. Sign-in = 5/min, sign-up = 5/hour, forgot-password = 3/hour. Disabled under `NODE_ENV=test`. For multi-instance prod, swap the `Map` for Redis — the `rateLimitCheck` interface is the same.
- **AI cooldown** (`apps/api/src/ai-cooldown.ts`): per-key in-memory cooldown for expensive AI endpoints — overview generation 30 s (per notebook), full reindex 60 s (per user), suggest-card 5 s and markup harvest 15 s (per source). Exceeding → 429 `{ error: 'cooldown', retryAfterMs }`. Disabled entirely under `NODE_ENV=test`; the pure `cooldownCheck(key, ms, now?)` (third arg = epoch-ms number, default `Date.now()`) is unit-testable with an injected clock. Web maps 429 cooldown to an info toast (not error).
- **Review inspector width**: the desktop card-information panel resizes from its left edge (220–420px, default 256), persisted as `nn:review:inspector-width`. The grid and loading layout consume the same CSS width variable. The resize edge stays fixed outside the scrolling contents; keyboard arrows and double-click reset use the shared ResizeHandle.
- **Sidebar width** (`apps/web/src/lib/ui-store.ts`): right-edge resize at widths ≥720px selects a 72px compact rail or 208–360px expanded sidebar (default 232; snap below 160px), persisted locally as `nn:sidebar-width`. The shell and WCO offsets consume the same value; tablet width preserves the manual choice; mobile drawer and hidden-sidebar behavior remain independent. Arrow keys resize, Home/End select bounds, and double-click restores the default. Chat uses a separate `nn:chat:rail-width` preference (220–420px, default 280; constrained to available space).
- **Deck organization**: `decks.position` persists sibling order (ties: name then id); `POST /decks/:id/move` atomically moves a subtree before/after/inside an owned target or to root. REST hierarchy mutations serialize per owner and reject cycles/foreign targets. Migration `0029_cooing_luckman.sql` is additive; deploy API before web and leave the column during rollback. Deck icons reuse the optional icon field with 48 searchable choices and fallback. The shared DECK_COLORS catalog has 30 values; additive migration `0030_colorful_ego.sql` extends only deck colors, keeping notebook colors unchanged. Dragging uses pointer capture and hit testing with Escape cancellation; touch retains the explicit move dialog. The deck workspace uses server study summaries/forecasts, never cached card counts. `useStudyForecast` normalizes Eden-revived dates into UTC day strings.

There are 37 palettes with paired modes (20 Reomi originals and 17 classic palettes); legacy string preferences migrate preserving their former appearance. `data-theme` selects the palette and `data-theme-mode` the resolved mode. `theme-catalog.ts` generates both CSS tokens and browser chrome colors; the same self-contained `theme-runtime.ts` runs before first paint and on live changes. OS changes in System mode and cross-tab storage changes are synchronized. Theme tests cover legacy migration, unavailable storage, every palette pair, contrast and prepaint parity.

BetterAuth's `emailAndPassword.sendResetPassword` calls `sendEmail`; the web side has `/auth/forgot-password` → token email → `/auth/reset-password?token=…`. All calls go via bare `fetch` on the client (not the BetterAuth SDK) so version bumps don't rename methods under us. The reset subject and body name the product Reomi. When `EMAIL_FROM` is empty the From stays `NeuroNexus <noreply@neuronexus.app>`; the code does not substitute `noreply@reomi.ru`.
- **GDPR**: `GET /profile/export` returns a full JSON dump of the user (profile, decks, cards, reviews). `DELETE /profile` (body: `{ confirmEmail }`) removes the user — FK cascades clean everything else. Covered by 5 integration tests.

The API image healthcheck calls `/ready`; neither endpoint exposes IDs, content, keys, or provider details.
- **Graceful shutdown**: SIGTERM, SIGINT, `uncaughtException`, and `unhandledRejection` share the memoized coordinator in `apps/api/src/shutdown.ts`. It marks readiness unavailable, stops the listener, drains all workers concurrently (including the `reminder` tick), and closes PostgreSQL within one `SHUTDOWN_TIMEOUT_MS` deadline (default 8000 ms). A shutdown signal stops a new reminder pass from reserving a slot; `GET /ready` exposes `workers.reminder`. Production `stop_grace_period` is 10 s. Fatal causes emit bounded `process.fatal` and request a non-zero natural exit; never add `process.exit()`.

## Personal MCP access

- **Endpoint:** `/mcp` is stateless Streamable HTTP with per-request personal bearer authentication, separate from cookie REST auth. Local/prod endpoints use their own configured databases and tokens. No provider keys required for deterministic tools. Full setup and tool catalog: `docs/mcp.md`.
- **Personal tokens:** Settings and session-only `/profile/tokens` create/list/revoke credentials (read or write scope, 1..365 days, maximum 30 active). Only SHA-256 digests are stored; full `nn_pat_` secrets appear once. Never log tokens, tool arguments, results or source/card content. Token auth MUST NOT become a general REST write bypass.
- **MCP writes:** all domain writes go through stored, ten-minute `mcp_actions` previews, bound to user and token. `confirm_action` requires an explicit client/user decision; validates the unchanged stored arguments/state and commits the mutation and consumption atomically. Client write approval remains required. JSON arguments are canonicalized before previews because JSONB reorders object keys. Index/source enqueue runs only after commit.
- **Adapters:** reuse chat tools and curated GET routes through a process-private Request identity map. Never accept identity headers or arbitrary methods/paths. Add management tools only with ownership checks, honest previews and transaction-aware execution. Test both scopes, cross-user and cross-token access, expiry/revocation, stale previews and concurrent replay.
- **Clients:** `bun run mcp:smoke` verifies a real HTTP SDK connection. `bun run mcp:stdio` bridges stdio-only clients. Canonical client variables are `REOMI_MCP_URL` plus `REOMI_MCP_TOKEN` or a private `REOMI_MCP_TOKEN_FILE`; `NEURONEXUS_MCP_*` remains a fallback and loses when both are set. These variables configure client scripts, not server credentials. The canonical endpoint is `https://api.reomi.ru/mcp`. The server name is `reomi`; listed resources are `reomi://guide` and `reomi://connection`. Reading `neuronexus://guide` or `neuronexus://connection` returns the same body and scope. This release uses PATs, not OAuth.

## Navigation continuity and study recovery

- Navigation metadata belongs to the account and current tab: `nn:navigation:v1:<owner>` in sessionStorage and the opaque `nnNavigation` history marker. Back/Forward addresses individual entries; sidebar/bottom-tab collection links use `intent: 'section'`; object links start explicit views. Reset clears browsing state but keeps appearance preferences. A fresh tab does not inherit another tab's journal. Navigation does not synchronize between devices.
- `AppNavigationProvider` merges its marker with Next history fields. A marked entry retains one previous same-path URL to cover reload racing consumed query cleanup. The opaque `nn:navigation:reload:v1` pagehide marker is a fallback only when Navigation Timing reports `reload` and the owner matches; never use it for new tabs or ordinary navigation. The pre-hydration bridge in `navigation-history.ts` captures native traversal before Next; do not monkey-patch router/history or replace this with a late popstate listener. `track:false` only suppresses route progress; `viewOnly:true` is reserved for internal same-path query cleanup that retains the mounted editor. Full navigation and browser traversal use the existing save/keep/discard/stay guard, including repeated Back while a decision is open.
- The journal accepts typed metadata only, not source/card bodies, editor buffers, assistant messages or grade payloads. Limits: 64 entries, 64 KiB per entry, 512 KiB total, 16 ancestors. Scroll reconstruction uses semantic first/last-visible anchors and unchanged opaque cursors, bounded to 20 pages, 10,000 rows and 5 seconds. Failed reconstruction retains filters and usable data with retry; user input/scroll, route, query or account changes cancel stale restoration. Refreshing a paginated list retains its loaded tail.
- Reader anchors are entry-specific: PDF page/fraction and text chunk/offset. Explicit passage links override remembered reading state; Back uses that entry's anchor even if a later visit updated server progress. Notebook readers use the shared full reader with `?source=` history. Saved note/artifact and inspected-card IDs are revalidated through owned reads. Restoration never generates an artifact, saves content or confirms assistant actions. Reload does not autofocus editable inputs.
- Authenticated routes mount only when session and bootstrapped profile owners match. Sign-out/account change invalidates the outgoing journal and pending reads. Same-owner reauthentication uses an opaque tab-local return marker; unrelated preferences and independently managed drafts are retained. Storage denial falls back to memory and shows a non-blocking notice.
- The existing `review-session.ts` owner, not the navigation journal, manages study checkpoints. `nn:study:checkpoint:v1:<owner>` retains the active card, compact queue/history, typed/revealed state, elapsed active time and an uncertain operation. Limits: 16 sessions, 512 KiB each, 3 MiB total, 1000 queued cards/confirmed answers, 16,000 answer characters. Capacity failures are visible and do not truncate prior work; navigation stores only the session ID.
- Migration `0036_special_dreaming_celestial.sql` adds review operation receipts. `POST /reviews/operations/:operationId` commits grade + receipt atomically under the existing owner/profile lock; matching retries return the same result, changed arguments return 409, and undo/deletion leaves a reverted tombstone. `GET` on that route resolves uncertainty; `GET /reviews/records?ids=...` verifies at most 100 owned review IDs without returning undo snapshots. Legacy `POST /reviews` remains compatible. Never automatically replay a grade on recovery.
- Review reload, reauthentication and focus/wake reconcile current versions and receipts before grading. A changed/deleted question preserves typed input until an explicit decision. Cross-tab grade/undo signals use `nn:study:changed:<owner>`; other clients are checked on focus. Active-answer time excludes pauses and unobserved sleep gaps; due comparisons use a monotonic server clock. Wake notifications coalesce during an active queue request; a slow empty response that crosses its learning deadline gets one compensating read.
- Rollout: apply the additive migration and compatible API before web. Prefer web-only rollback; keep receipt data/schema and the compatible API available for pending operations. An older API cannot accept the versioned grade URL while silently ignoring operation identity. Browser evidence and release gates are recorded in `openspec/changes/archive/2026-09-23-preserve-navigation-context/acceptance.md`; the reusable Next history proof is `apps/web/scripts/navigation-browser-proof.mjs`.

## Operations and recoverable small actions

- `GET /operations/v1` projects accepted source ingest/reingest and source/notebook artifact runs (including quizzes), with active/attention/recent groups and per-group opaque cursors (20 rows, max 50). Active jobs have no age cutoff; attention/recent use the latest run's terminal time within seven days. Upload transfer, overview/global reindex and chat are outside this list. Reading and search capabilities are separate; keep original-PDF and parsed-text availability truthful.
- Migration `0037_special_loners.sql` adds current run identity/timestamps, persisted generation options and retry receipts. Every start path advances run identity; worker persistence is fenced by the captured run. `/operations/v1/retry` commits one conditional replacement run and receipt before enqueue, preserves quiz settings, and never automatically replays on reconnect. Legacy missing settings require explicit defaults. Reconciliation exposes interrupted artifact jobs as failures.
- The shell owns one account-keyed observer (2.5 s active / 30 s idle, bounded backoff, focus refresh, hidden-tab suspension). Source/artifact status hooks consume its invalidation with coalesced slow reads; full artifact content streaming is separate. Keep stale rows on observation errors and retain focus across run changes. Operations remains reachable with the sidebar hidden and on mobile.
- Migration `0038_fancy_yellowjacket.sql` adds UI-action receipts and SQL metadata/hierarchy revisions covering legacy and assistant writers. Versioned `/ui-actions/v1` adapters preserve card/note-type versions and destructive previews; include written study notes, source title/author/description/tags, notebook title, deck name/color/icon and deck moves. Cookie auth only; no PAT or assistant-approval bypass. Body-write receipts store hashes/identities, not copied content. Migration `0039_daily_ken_ellis.sql` adds the session/order index; retain the matching `DESC NULLS LAST` offer order. Migration `0040_note_operations.sql` adds owner-scoped note-create receipts. ## Product shape

**Reomi** is a reimagined Anki (spaced-repetition flashcards) with a graph view, garden gamification, and AI affordances. The architecture is **server-of-truth over Bun + Elysia + Postgres**, with a Next.js/React 19 client. Auth via BetterAuth. No offline mode yet — every page requires a logged-in session; the client is a thin mirror of the server's state.

The app was first built client-only against Dexie, then migrated to the current server-first shape. Expect occasional leftover files or comments from the Dexie era; delete on sight if they're clearly orphaned.

## Backend architecture (apps/api)

### Entry point
`apps/api/src/index.ts` starts the app built by `apps/api/src/app.ts`, registers the shared shutdown/fatal handlers, and kicks root-scoped reconciliation. `buildApp()` composes CORS/Swagger, derived request context, `/health` + `/ready`, safe error handling, auth, and domain modules. **Do not `export default app`** — if you do, Bun auto-binds `Bun.serve(app)` and collides with the explicit `.listen()` call. Only export `App` as a type for Eden Treaty.

### Auth plugin
`apps/api/src/auth-plugin.ts` both `.mount(auth.handler)` (exposing `/api/auth/*`) **and** defines a reusable `auth: true` macro that resolves `{ user, session }` or returns 401. Every protected route passes `{ auth: true }` in its route config — this is how the route gets typed access to `user.id`.

### Domain modules
Each under `apps/api/src/modules/*.ts`, prefixed with its resource (`/decks`, `/cards`, `/reviews`, `/profile`). All operations scope by `user.id` pulled from the session. FK `ON DELETE CASCADE` on `decks.parent_id`, `cards.deck_id`, `reviews.card_id` and `.deck_id` means deleting a deck cascades the full subtree at the DB level — do NOT re-implement the cascade in the handler.

### FSRS grading
`apps/api/src/modules/reviews.ts` reconstructs a `ts-fsrs` Card shape from the flat Drizzle columns, calls `gradeFsrs` from `@reomi/shared` with the user's `desiredRetention`, then writes back the new FSRS state + a `reviews` row + an updated `profile` (streak/xp/level/plantStage) inside a single `db.transaction`. Keep the entire grade rollup transactional; a partial card/review/profile write corrupts scheduling and gamification even though the app now has other multi-table workflows too.

**Leech auto-suspend:** after a grade, if `card.lapses` crosses the threshold (Anki default: 8), `suspended` is set to `true` in the same transaction and the response includes `leeched: true`. Subsequent `POST /reviews` on a suspended card returns 409.

**XP formula:** `{ Again: 0, Hard: 5, Good: 10, Easy: 15 }` — defined in `xpForRating` in `@reomi/shared`. Formula lives there, not in the handler, so the web app can preview deltas client-side.

### Review queue
`GET /cards/queue?deckId=…&newLimit=20&reviewLimit=200` returns `{ due, new, total, mode, summary }` for regular study. Due learning/relearning comes first and bypasses the mature-review daily cap; mature reviews consume the review budget and first introductions consume the new budget. Both lanes have stable ID tie-breaks. Regular responses are bounded to 500 cards; filtered sessions keep their configured limit up to 1000. All study queues exclude suspended cards. `summary` reports full scoped counts, remaining budgets and the next learning time. Use this endpoint for the reviewer, never the paginated card mirror.

## Study-session reliability

- **Grade/undo consistency:** `reviews.ts` creates a missing profile idempotently and locks the profile before the card. Both grade and undo follow this order. Optional `expectedReps` + `expectedUpdatedAt` reject stale grades with 409 `card_changed`; optional undo `reviewId` rejects an obsolete session with 409 `review_changed`. Legacy request shapes remain accepted. Manual card/note changes advance `updatedAt` monotonically so undo cannot overwrite them within the same millisecond.
- **Study time:** one answer is capped at `MAX_REVIEW_DURATION_MS` (10 minutes). The API sums today's persisted durations before rounding to integer minutes; sub-minute answers count toward the daily goal. Web time pauses while hidden, saving or waiting. Those minutes belong to the open study-day interval.
- **Study day:** the study day is the profile epoch `[study_epoch_start, study_epoch_end)` plus `study_day_policy`. A missing policy row is legacy UTC midnight. Saving a zone or rollover does not move an open interval. The next budget starts at the stored end and runs to the end of one study-day label, so a later rollover's morning stub is not a second budget and the new label is never the closed epoch's label. Chart queries keep a review on its stored `study_day` when that instant sits outside the new zone's span. Reminder `notification_settings.time_zone` is not that clock and stays on `todayISO`. Migration `0044_study_day.sql` backfills existing rows as UTC dates.
- **Full counts:** `GET /cards/study-summary` (`modules/study-summary.ts`, shared `StudyOverview`) aggregates every owned card, includes descendants per deck, applies effective limits and exposes no card content. Home, decks, sidebar, bottom tabs and the app badge use it through the existing session-resource cache. Forecasts come from `/stats/forecast`, with the server's study-day labels; unavailable data is not zero.
- **Reviewer:** `lib/review-session.ts` holds pending cards and confirmed answers. Short regular learning steps (up to 20 minutes) remain pending until due; the reviewer refetches at a batch boundary or next due time. Filtered sessions remain finite and change scheduling without consuming regular daily counters. Skip moves an unanswered card to the end; only undo returns to a saved answer. There is one owner/scope-bound in-memory editor handoff so Save/Cancel/Back can resume the same card and tallies; logout clears it. Full reload starts a new local session from the saved server schedule.
- **Editor/mutations:** grade/undo/control responses are bare rows; preserve embedded note/type/tags with `mergeReviewedCard`. Note create/update responses are enriched from their returned note and the loaded type. Optional `PATCH /notes/:id { deckId }` moves the note's generated cards atomically with content while preserving FSRS. The editor explains note-wide effects. Empty generated card sets on POST return `no_cards_generated`; UI catches missing cloze prompts and retains drafts on error.
- **Bulk scheduling:** `/cards/bulk` accepts `forget` and `setDue` (`payload.setDue`), in addition to existing actions. One owned selection is one SQL update (max 1000 IDs); scheduling actions return updated cards. Invalid dates fail before writing. Browser selection is cleared when changing filters and cannot mutate stale search results.
- **Results/accessibility:** `lib/study-result.ts` validates and scopes summaries to the user, distinguishes answers from unique cards, and falls back to memory when storage is unavailable. Undo invalidates the result. The rating footer is outside the card scroller; keyboard handling respects inputs, IME, modifiers and dialogs. Root HTML intentionally suppresses only the expected theme-bootstrap attribute mismatch. Reduced-motion styles cover review transitions and overlays.
- **Acceptance:** `docs/spaced-repetition-acceptance.md` records the release matrix and rollout/rollback order; the ordered checklist is under `openspec/changes/archive/2026-09-22-polish-spaced-repetition/tasks.md`.

## Database (packages/db)

- `schema/auth.ts` — BetterAuth tables (`user`, `session`, `account`, `verification`). Regenerate with `bun run --filter @reomi/auth auth:generate` if you add plugins.
- `schema/app.ts` — all domain tables: profiles/decks/notes/cards/reviews, AI conversations/index rows, media, sources/library/provenance, and notebook artifacts. FSRS state is flattened into card columns; `due` is indexed with `user_id` for the review queue. Keep ownership FKs, cascades, partial indexes, and pgvector constraints synchronized with versioned SQL.
- `client.ts` — singleton `postgres()` pool + `drizzle()` instance. Use `db` + `schema` from `@reomi/db`.
- `drizzle.config.ts` — the `loadRootEnv()` function walks up from `packages/db` to parse the root `.env` manually, because drizzle-kit spawns a Node subprocess that doesn't inherit Bun's auto-loaded env. Don't replace this with `dotenv` — it's intentionally zero-dep.

**Schema changes workflow:** production, dev, and the disposable test database are built from the committed SQL chain (`db:migrate:apply` / `db:migrate:apply:test`). `drizzle-kit push --force` cannot reproduce ordered backfills, the 0027 cloze constraint, or the 0038 triggers through chain head `0042_youtube_source.sql`; it is limited to `TEST_DATABASE_URL` and never opens `DATABASE_URL`. Local `bun run test` applies migrations before the suite. CI applies `db:migrate:apply:test` and runs `test:ci`, which has no schema-push hook.

## Frontend architecture (apps/web)

### Server-first data flow
- `src/lib/api.ts` — **Eden Treaty** client: `treaty<App>(baseURL, { fetch: { credentials: 'include' } })`. `credentials: 'include'` is mandatory — without it BetterAuth session cookies don't cross the :3000↔:3001 boundary. Also exports `ok(result)` which unwraps Eden's `{ data, error }` envelope and throws on non-2xx. Ordinary JSON domain calls go through Eden; deliberate raw-fetch exceptions include BetterAuth password-reset flows, SSE chat, binary annotation payloads, and presigned S3 uploads. Keep credentials/error/request-id behavior explicit in those exceptions.
- Eden's inferred types occasionally choke on the store's generic patch handlers; calls in `store.ts` cast through `(api as any)` intentionally. When adding new endpoints, start without the cast — only fall back to `any` if TS explodes on `treaty<App>` path chains.
- `src/lib/store.ts` — Zustand store. Each method translates to one API call; the store holds a cached mirror for synchronous reads in components. No more Dexie.
- `src/lib/mappers.ts` — converts server rows (ISO dates, column names like `learningSteps`) into the UI types in `lib/types.ts` (epoch numbers, camelCase, reconstructed FSRS Card). If you add a column, extend the mapper, not the component.

## Gamification (shared + reviews handler)

The grade handler is the single place where gamification state advances. It calls `applyGradeRollup` from `@reomi/shared` inside the same transaction that writes the FSRS card + review row. Rollup semantics:

1. **Streak + freeze:** `applyStreakWithFreeze` bumps `streak_days` when yesterday=last-review, consumes a freeze when there's a **one-day** gap (multi-day gaps always reset), and resets otherwise. Capped at `MAX_STREAK_FREEZES` (5). Freezes are **never replenished** (the achievement-reward path that used to top them up was removed).
2. **Today minutes ledger:** `today_minutes` + `today_minutes_date` accumulate `durationMs` across grades within the same calendar day; reset when a new day arrives.
3. **Daily goal stamp:** once today's minutes cross `daily_goal_minutes`, `daily_goal_met_count` increments **once** per day.
4. **XP + level:** `ratingXp = xpForRating(rating)` (`Again=0, Hard=5, Good=10, Easy=15`); `level = floor(xp / 500) + 1`. No achievement bonuses — the only XP source is grading.
5. **Plant stage:** `plantStageFromStreak(streak)` in `packages/shared/src/fsrs.ts` maps the current streak to a 0–5 stage displayed in the garden.

**Plant species:** all six species (`fern`, `cactus`, `succulent`, `bonsai`, `sakura`, `mushroom`) are available to every user by default — the achievement-gated unlock flow was removed. `profile.plant_species` stores the current selection; `profile.unlocked_species` is kept in the schema for forward-compat but is no longer enforced.

`POST /reviews` response carries `{ card, review, profile, leeched, freezeUsed, dailyGoalJustMet }`.

**Achievements module removed (2026-06-06).** `evaluateAchievements`, `ACHIEVEMENTS`, `sumRewards`, `GET /achievements`, `GET /achievements/summary`, `GET /achievements/catalog` no longer exist. Do not try to call or import them.

## Shared FSRS (packages/shared)

`packages/shared/src/fsrs.ts` wraps `ts-fsrs` for both server (grading) and client (rating preview). Use `Rating 1|2|3|4`, mapped to FSRS `Grade` via `ratingMap` — do NOT use `FsrsRating` directly (it includes `Manual`).

`getScheduler({ requestRetention, enableFuzz, deterministicSeedCardId })` memoizes one `fsrs()` instance per unique cache key. This lets per-user `desiredRetention` work without allocating a scheduler on every call. In tests, pass `{ enableFuzz: false }` for exact-`due` assertions.

Anki-compatible defaults exported as `ANKI_DEFAULTS`: `requestRetention=0.9`, `learningSteps=['1m','10m']`, `relearningSteps=['10m']`, `leechThreshold=8`, `maximumInterval=36500` days. Keep this module the single source of truth for those numbers — the reviews handler imports them; don't inline magic constants.

Streak / XP / plant-stage helpers (`nextStreak`, `xpForRating`, `levelFromXp`, `plantStageFromStreak`) are here too, so both the grade handler and UI previews agree.

## Testing

- **Test runner:** `bun test` (built-in). Files: `*.test.ts` anywhere in the tree. `bun run test` at the root runs every suite after `bun run db:migrate:apply:test` (the `pretest` hook). `bun run test:ci` is the same runner with no lifecycle hook, so CI can apply migrations itself and then test that schema. CI workflows must not call `bun run test`.
- **Test database:** `TEST_DATABASE_URL` points at `neuronexus_test`, created by `docker/postgres-init.sh` on first container boot. `packages/db/src/env.ts` switches to it automatically when `NODE_ENV=test`, so there's no way to accidentally hit the dev DB from tests.
- **Integration pattern:** tests import `buildApp()` from `apps/api/src/app.ts` and call `app.handle(new Request(...))` — no network, no port binding. Helpers in `apps/api/tests/helpers.ts` wrap body/cookie serialization (`callApp`), cookie extraction (`extractCookie`), and sign-up (`signUpAndCookie`). Every `beforeEach` calls `resetTestDb()` which `TRUNCATE … RESTART IDENTITY CASCADE`s the full domain + auth table set (refuses to run unless the URL contains "test").
- **FSRS tests use `{ enableFuzz: false }`** to make `due` assertions stable. If you need fuzz on in a specific test (e.g., testing the fuzz bounds), pass `deterministicSeedCardId` to pin the RNG.

## Builtin note types

Migration `packages/db/src/migrations/0007_builtin_note_types.sql` seeds the three system note types (Basic, Cloze, Type-in) on every fresh database via a partial unique index `note_types_builtin_uq` + `INSERT … ON CONFLICT DO NOTHING`. This replaced the old seed-only path that made note-type creation impossible on prod without a manual seed run.

`ensureBuiltins()` from `@reomi/db` (`packages/db/src/ensure-builtins.ts`) is the test/startup contract — call it in `beforeEach` helpers and at API startup to guarantee the three rows exist before any note-type-dependent operation. `BUILTIN_NOTE_TYPES` UUIDs are valid for fresh seeded databases and fixtures, but long-lived databases may retain legacy builtin rows because the migration used `ON CONFLICT DO NOTHING`. User-facing create/write paths MUST resolve the live note type (`resolveNoteTypeForCreate`) and map field names case-insensitively; never trust a builtin UUID literal as the only lookup.

## Undo (POST /reviews/undo)

`POST /reviews/undo` atomically reverts the most recent grade for the authenticated user. The grade handler stores a `undo_snapshot` JSONB column (migration `0008_undo_snapshot.sql`) on the `reviews` row at write time, capturing the exact pre-grade card + profile fields. Undo reads the snapshot and restores those fields — including `updatedAt` — in a single transaction.

Error boundaries:
- Double-undo → 404 (snapshot cleared after first undo)
- NULL snapshot (legacy row) → 404
- Card mutated after the grade via `forget` or `setDue` → 409 (guards against restoring stale FSRS state)
- Suspended/leeched card — undo still works; leech state is part of the snapshot

Side-effect: restoring pre-grade `updatedAt` means the card won't appear at the top of `edited:` / `sort:updated` queries after an undo — this is intentional (it wasn't edited, it was reverted).

UI surface: `⌘Z` keyboard shortcut + explicit undo button inside the reviewer. Both dispatch the same store action.

## Forget / set-due (PATCH /cards/:id)

`PATCH /cards/:id` accepts two new optional fields alongside the existing patch surface:

- `forget: true` — resets the card to a fresh FSRS state via `fsrsResetColumns` (stability/difficulty/interval zeroed, state=New, lapses unchanged). Clears `suspended`.
- `setDue: <ISO string>` — overrides the `due` timestamp without touching any other FSRS field.
- Combining both in one request → 400.
- Invalid ISO date for `setDue` → 400.

The handler uses **explicit field mapping**, not a body spread, so unknown fields are silently ignored rather than applied to the row. Add new patchable fields to the explicit map if needed — never destructure the whole body into the update.

## Rich card content

Card fields are stored as lossless Markdown source. `sanitizeFieldValues` retains its historical name but does not interpret source as HTML; `sanitizeFieldHtml` is reserved for explicit HTML callers. Render with `markdown-it` (`{ html: false, linkify: false }`) field-by-field inside `apps/web/src/lib/render-card.tsx`, then always sanitize rendered HTML. Never inject stored source directly. Syntax highlighting uses highlight.js in class-based mode (no inline styles); the theme lives in `apps/web/src/app/globals.css`. Mermaid diagrams are rendered asynchronously via `RichCard` with a dedicated SVG sanitizer.

The shared Markdown parser also derives search text, preserving code such as `Array<T>` while excluding media URLs. Repair old disposable columns using `bun --env-file=../../.env src/ai/rebuild-card-text.ts <userId>` from apps/api; `--reindex` additionally awaits embedding batches (usual capability/degradation gates apply). The repair is user-scoped, bounded, idempotent and does not change source, FSRS or card versions. Already lost source cannot be reconstructed from the cache.

Numbered cloze: `cards.cloze_number` is null for ordinary cards, 0 for legacy aggregate questions and positive for one cloze group. New notes generate one card per distinct number per template; repeated numbers belong to one question. Migration `0027_dazzling_madame_masque.sql` preserves every existing card/FSRS/review row, marks old cloze rows as aggregate and adds a `UNIQUE NULLS NOT DISTINCT (note_id, template_ord, cloze_number)` constraint. Stable template IDs are mapped to their current ordinals atomically; reconciliation keys also include the cloze number. Duplicate preexisting identities make the migration fail without deleting data. Legacy rows written without the new column by an older API are recognized as aggregate until upgraded.

The balanced parser in `packages/shared/src/cloze.ts` supports hints (`{{c1::answer::hint}}`), braces/formulas and up to eight nested levels; new generation is capped at 128 cards per note. Markdown code spans/fences/indented code and escaped literal examples do not create questions. New cloze requires a real positive-number deletion; historical aggregate syntax remains readable, including old c0 usage. Malformed new content is a 400; malformed historical display degrades to an authoring error without revealing partial answers. Math containing cloze is transformed before KaTeX, and unused/hidden diagram islands are not rendered.

Existing aggregate notes only split through an explicit note preview/PATCH with `clozeRetainHistoryFor: { [templateOrd]: clozeNumber }`. Every old template needs a destination. The chosen question keeps its card ID/history/schedule and other numbers start new. Consent binds that map and current versions; note create/edit accepts `expectedTypeUpdatedAt` from the displayed definition. The editor previews every generated question, explains omitted optional templates, and re-hides the answer when switching previews. Deploy API/schema before web; once numbered cards exist, reverting to an application that assumes one card per ordinal requires a verified data restoration or a compatible forward fix, not simply dropping the column.

Note-type fields/templates carry stable optional `id` values in JSON. Existing definitions receive deterministic legacy IDs at read time and persist them on edit; new definitions use UUIDv7. Renaming fields migrates their values and template references atomically; template reorder remaps card ordinals by identity without reassigning FSRS history. Preserve these IDs in editors and API clients. Type edits reconcile created/surviving/removed cards by stable identity. `POST /note-types/:id/preview` and `POST /notes/:id/preview` are read-only previews with counts, bounded removed-card summaries and a consistency token. Deleting generated cards requires that exact token at PATCH time; changed notes/types/cards/history invalidate it. Pass `expectedUpdatedAt` from the displayed note/type to reject stale editors. Keep previews on dedicated POST URLs: sending a preview flag to an old PATCH handler could accidentally mutate.

Internal note writes lock type → note → cards and check resolved versions, including AI/reading-born creation. Type edits enqueue only changed search text/new cards after commit; removed cards cascade their index. `edit_card` stores the server-generated preview token on the pending tool-call JSON, checks it on resume and keeps field edits plus card moves in the same transaction. Legacy pending edits without a token fail safely and need a new proposal.

After a type mutation, the web atomically refreshes the type and loaded cards (including deep/suspended cards via bounded `POST /cards/lookup`, max 200 IDs, plus `/cards?noteTypeId=` for new rows). Delete removes affected mirror rows. A revealed reviewer retains its displayed content and requests an explicit refresh when its type changes. Failed/stale editor writes retain the draft and offer the latest saved fields/definition for comparison.

Migration `0026_nebulous_havok.sql` makes historical `reviews.deck_id` nullable with `ON DELETE SET NULL`: moving a card then deleting its former deck preserves its review history. Deleting the card itself still cascades. Treat null as a deleted historical location, never as permission to widen a user/deck scope. Do not restore the old NOT NULL/CASCADE constraint by deleting retained history.

**`RichCard` is the single rich-content render component** — used for cards in the reviewer/form/browser, note-type previews, and generated artifact documents (via the artifact note-type shim). Never render raw field/artifact HTML outside of it.

Per-type CSS is legacy metadata only: the type editor no longer offers an editable control that claims to style cards. Previously saved CSS remains read-only and is preserved in saves/exports. Mermaid uses the active Reomi palette tokens via the base theme, observes both `data-theme` and `data-theme-mode`, serializes configuration/render pairs and discards outdated asynchronous results. Pending diagrams show a localized loading state rather than internal placeholder IDs; SVG sanitization remains mandatory.

Render pipeline order matters:
1. Shared `cardMathPlugin` and `cardClozePlugin` parse formulas/deletions in Markdown context before escapes consume their syntax. Code remains literal; display math can span blank lines. Never restore the old whole-source regex replacement, which interpreted examples inside code.
2. Main DOMPurify sanitization runs on the markdown output.
3. Mermaid SVG islands are injected **after** main sanitization via a single `inject-node` pass (they cannot pass through the main sanitizer).

## Sanitizer (DOMPurify allow-list)

The main sanitizer allow-list was extended to cover rich Markdown output: `h1`–`h6`, `blockquote`, `pre`, `code`, `a`, `table`, `thead`, `tbody`, `tr`, `th`, `td`. The extension is symmetric — both the card-render edge and the note-type-editor preview edge use the same config, pinned by a bypass corpus in the test suite.

`<a href>` whitelisting is enforced via a `uponSanitizeAttribute` hook that permits only `https?:` and `mailto:` schemes. The previous `ALLOWED_URI_REGEXP` approach was removed in favour of the hook — do not re-introduce the regexp.

`style` attributes remain **blocked** in the main sanitizer. KaTeX and Mermaid output passes through isolated sink configs that allow `style` only for their respective output nodes (`KATEX_DOMPURIFY_CONFIG`, `MERMAID_DOMPURIFY_CONFIG`). `MEDIA_TOKEN_RE` is unchanged.

`Deck.parentId?: string` gives Anki-style hierarchy. ## Conventions & gotchas

- **Client-everywhere for screens:** every `(app)/*/page.tsx` is `'use client'`. Server Components that call `auth.api.getSession()` for SSR are OK outside the app group, but the app shell depends on client state.
- **`useSearchParams` + Suspense:** wrap consumers in `<Suspense fallback={null}>` (see `/editor` and `/auth/sign-in`).
- **Don't split screens into client+server halves** to save bundle size — dynamic topbar subtitles depend on the store.
- **Root `.env`:** the api loads it via `bun --env-file=../../.env` in its `dev` script. Next reads `apps/web/.env.local` when present; if browser-facing values need local overrides, symlink that path to `../../.env` rather than maintaining a second env file. Local URL fallbacks work without the symlink. Production `NEXT_PUBLIC_*` values come from Docker build args.
- **No default export from apps/api/src/index.ts** — Bun's auto-serve would collide with `app.listen()`.
- **Deck deletes cascade** at the DB level (FK `ON DELETE CASCADE`). The `decks.deleteConfirm` i18n message already spells out the subtree warning — keep it accurate if you change deletion semantics.
- **Remote cron trigger** (`trig_01VB9fKge65wEAm4VDzDDEEw`) runs hourly and opens PRs that fix non-working frontend UX (originally scoped to the Dexie era, still useful for mocked buttons / broken interactions). Small focused PRs from that agent are authoritative bug fixes — review and merge normally. If the PR references a feature that now depends on the backend, verify the API path actually exists before merging.
- **`AGENTS.md` mirrors this file's body** for Codex; only the title and introductory sentence differ. After editing CLAUDE.md, copy it to `AGENTS.md`, restore the Codex header, and verify the remaining diff contains only those two header lines.

- **Typed answers / definition validation (round 2):** `NoteField.typeinAnswer` pins one answer role by stable field identity; migration `0028_broad_blizzard.sql` assigns the old last-by-ord field on legacy Type-in definitions and adds `notes.accepted_answers` (`text[]`, empty by default). The note editor authors explicit alternatives (20 × 256 chars); omitted alternatives survive ordinary API/AI edits. Review compares shared `fieldPlainText()` against the canonical answer or an exact explicit alternative (`typedAnswerTarget`), normalizing NFC/case/edge whitespace only, and never auto-grades. Card DTOs carry fields and alternatives with their note/type version. Shared definition validation rejects ambiguous field names, unknown references and unbalanced conditions; type previews test existing notes with bounded samples and block unusable notes. The shared generator determines question fitness; the first field is not inherently required. Raw HTML-only img fields receive a format error; Markdown `/m/<uuid>` media questions are supported.

- **Rich-content diagnostics / kind conversion (round 2):** visible math/diagram failures carry field + per-field block metadata to escaped diagnostic islands in the existing `SafeHtml` sink. Both schemas, notes, mapping choices and current card/review state bind the confirmation token. Budget failures roll back and clear pending index IDs. Only actual definition changes regenerate cards; metadata-only name edits remain available on large types.
